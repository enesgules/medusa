This documentation provides a reference to the `sdk.auth.listProviders` method used to send requests to Medusa's Authentication API routes. It can be used for admin users, customers, or custom actor types.

This method lists the authentication providers available for an actor type.
It sends a request to the [List Auth Providers API route](/api/admin).

This is a public, pre-authentication endpoint. A frontend can use it to
render the available login options, such as an email/password form or
"Continue with ..." redirect buttons, based on each provider's `flow`.

## Example

```ts
const { providers } = await sdk.auth.listProviders("user")
```

<a id="listproviders-parameters" />

## Parameters

**listProviders**

- `actor`: `string` — The actor type. For example, `user` for admin user, or `customer` for customer.
- `headers`: [ClientHeaders](/resources/references/js_sdk/admin/types/js_sdkadminClientHeaders) (optional) — Headers to pass in the request.
  - `tags`: `string`\[] — Tags to cache data under for Next.js applications. Learn more in [Next.js's documentation](https://nextjs.org/docs/app/building-your-application/caching#fetch-optionsnexttags-and-revalidatetag).

<a id="listproviders-returns" />

## Returns

**listProviders**

- `Promise`: Promise\<[AuthProvidersListResponse](/resources/references/types/HttpTypes/interfaces/typesHttpTypesAuthProvidersListResponse)> — The list of available auth providers.
  - `providers`: [AuthProvider](/resources/references/types/HttpTypes/interfaces/typesHttpTypesAuthProvider)\[] — The list of auth providers.
    - `id`: `string` — The registered instance ID of the provider, used in authentication routes (for example, `okta` in `POST /auth/user/okta`).
    - `identifier`: `string` — The provider's static identifier (for example, `oidc` or `emailpass`).
    - `display_name`: `string` — The name to display for the provider in a frontend application.
    - `flow`: `"credentials"` | `"redirect"` — The authentication flow the provider uses: - `credentials`: the client submits credentials (for example, email and password) directly to the authentication route. - `redirect`: the client is redirected to the provider (for example, an OIDC identity provider) and returns through a callback. A frontend can use this to decide whether to render a credentials form or a "Continue with ..." redirect button.
